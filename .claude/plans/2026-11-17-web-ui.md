# Admin/status web UI

## Goal

A small web UI in the daemon:

- status of the bridge: DVR session, per-channel video statistics, RTSP clients, recent log events; no video;
- the DVR's settings, read and written through the DVR's own web settings API (see `docs/protocol.md`, "Web settings
  API"), with the field table from the same section.

The daemon itself never writes DVR settings; only a logged-in user's explicit form submission does.

## Decisions

- **Stdlib only:** `net/http` + `html/template`, no JS framework, no JS needed at all (plain forms). One embedded CSS
  block. Works in any browser and with curl.
- **Config:** `[web] enabled` (default false: the UI handles DVR credentials, so it is opt-in) and `listen` (default
  `:8090`). `[dvr] web_port` (default 80) is the DVR's HTTP port for the settings API.
- **Authentication passes through to the DVR:** the login form takes DVR credentials and verifies them with
  `perm.xml?p=0..9`; the login succeeds when at least one right is granted (a wrong password grants none). The
  credentials live only in the in-memory session (never on disk, in the config or in logs); the session id is a
  random cookie (`HttpOnly`, `SameSite=Strict`), idle timeout 30 min, logout drops it. The bridge config holds no
  admin credential.
- **Login rate limit:** after 5 failed logins within a minute from one client IP, or 20 in total, the login answers
  429 without contacting the DVR, so the UI cannot be used to hammer the DVR's accounts (each attempt costs ten
  `perm.xml` requests).
- **Permissions are the DVR's:** each settings page records its right (`p=7` for the settings window, `p=0` for
  accounts); without it the page is read-only (and the DVR's own `r=30` answer is shown as "permission denied").
- **Writes:** read the page, take the edited fields from the form, build the write request the DVR's own form would
  send (same field order, the same conditionally omitted fields, the read value for every untouched field), send it,
  read the page again and show the before/after diff. CSRF: a per-session token in every form, checked on POST.
- **Secrets are never displayed:** password fields (`CgiAuth` `p<i>`, Network `ppp`, `ddnpw`, the mail/CMS
  passwords) show as "set"/"empty"; an empty input keeps the current value. Account administration (`CgiAuth`) is
  read-only in the UI: writing it would resend every password.
- **Actions are not offered:** `CgiAddUser`, `CgiDelUser`, `NTPClient`, `AutoADJ` (side effects) are listed in the docs
  only; the UI never calls them.
- **Per-channel pages** use `ch=1..N`; the DVR UI's "all" mode is not offered.
- **Status data:** the RTSP servers expose counters (frames, bytes, last IDR, readers); the DVR client state comes
  from its callbacks; recent events from a ring-buffer `slog` handler (last 200 records, info and above).

## Packages

| package | content |
|---|---|
| `internal/dvrweb` | client of the settings API (cookie auth, `_=` query, `r` codes), page/field table, write builder |
| `internal/webui` | sessions, login/logout, status page, settings pages, CSRF |
| `internal/logring` | `slog` handler keeping the recent records |
| `internal/fakedvr` | `/gw` endpoints for tests: perm, read and write of a few pages, `r=11`/`r=30` |

## Tests

- `dvrweb`: XML parsing, error codes, the write request order and omissions (against the fake DVR web server).
- `webui`: login (good and bad credentials), session expiry, permission-limited read-only view, CSRF rejection,
  a write with the diff shown, secrets never in any response body.

## Open points

- The reply of a write (`<Page>A.xml`) is not documented; anything but an `r` error code counts as success, and the
  re-read is the real check.
- Whether the DVR accepts writes without the fields its own form leaves out (disabled ones) is open; the UI sends
  exactly what the DVR's form sends.
